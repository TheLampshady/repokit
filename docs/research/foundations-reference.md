# Foundations — Reference

Background research for repokit's "foundations" concept: what to call the shared, testable, decoupled, DRY building blocks at the base of a codebase, how teams document them, how they detect when those abstractions go bad, and who owns them.

This doc is reference material for the design of:

- a `FOUNDATIONS.md` registry generated by **dockit**
- per-foundation subject-matter-expert subagents generated by **agentkit**
- foundation-health signals emitted by the **auditor** agent
- foundation-related tickets written by **modernizer** (in the sibling [tikkit](https://github.com/TheLampshady/tikkit) plugin)

It does not specify implementation. It captures the terminology and prior art so design decisions have a paper trail.

**Revised 2026-08-02** — added § 3's key-class-detection findings and the layer-foundation category, the ranking-tool wrap-vs-build resolution, and § 6's coverage-pressure counterweight. Positions from working discussions rather than published sources are marked **(repokit hypothesis)**: unmeasured, to be validated by experiment.

## 1. Terminology

The industry has many words for "shared, foundational code." None is universal. The table below summarises which terms carry which meaning so we can pick deliberately.

| Term | Origin / community | What it names | Flavour | Verdict |
|------|--------------------|---------------|---------|---------|
| **Foundation** | Informal | Role in the codebase | Neutral | **User-facing label.** Already adopted by repokit. |
| **Core / `core/`** | Universal directory convention | An implementation location | Neutral | A hint, not the concept. |
| **Shared Kernel** | DDD (Eric Evans) | Pattern + entity that two contexts deliberately share | Backend-leaning | **Borrow the discipline.** DDD's rule: keep it small; growth is a smell that contexts should be merged or split. |
| **Component** (Backstage) | Platform engineering | A registry entry (one row in a software catalog) | Neutral | **Adopt as registry vocabulary.** Backstage's `kind: Component` with `spec.type`, `spec.lifecycle`, `spec.owner` is the cleanest schema in the wild. |
| **Software Catalog** | Backstage / Spotify | The registry itself | Neutral | **Adopt as the index concept.** `FOUNDATIONS.md` is a catalog. |
| **Paved Road / Golden Path** | Netflix / Spotify | Templates for *building new things* | Neutral | Different concept. About starting points, not existing shared code. |
| **Platform code** | Team Topologies | Code owned by a Platform team | Neutral | Implies a team boundary; useful for ownership only. |
| **Ports & Adapters / Hexagonal** | Cockburn | Boundary technique | Backend-leaning | A pattern for *building* foundations, not a registry. |
| **Anti-corruption layer** | DDD | Specific subtype of boundary | Backend | Subtype only. |
| **Design system** | Frontend | Visual + component foundation | Frontend | Frontend subset; one possible foundation type. |
| **Building block / Primitive** | Generic | Entity | Neutral | Vague but readable in prose. |
| **Module / Library** | Generic | Entity | Neutral | Too generic — every dependency is a "library." |

**Recommendation.** Use **foundation** as the noun in user-facing text. Internally model as a **Catalog** of **Components**, taking the field set from Backstage and the size discipline from DDD's Shared Kernel.

## 2. Documentation patterns

How teams in the wild write down what their foundations are.

1. **ADRs (Architecture Decision Records).** Short markdown per decision: status / context / decision / consequences. Lives in `docs/adr/`. Captures *why* a foundation exists and *why* it has its current shape — not the API surface itself. ([adr.github.io](https://adr.github.io/), [Fowler](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html), [MADR template](https://adr.github.io/madr/), [joelparkerhenderson collection](https://github.com/joelparkerhenderson/architecture-decision-record))
2. **Backstage `catalog-info.yaml`.** Per-component YAML next to the code. Fields: `kind`, `spec.type`, `spec.lifecycle`, `spec.owner`, `spec.providesApis`, `spec.dependsOn`. The de-facto standard for "list of things in our system." ([Backstage Software Catalog](https://backstage.io/docs/features/software-catalog/), [System Model](https://backstage.io/docs/features/software-catalog/system-model/))
3. **Module README.** Co-located with the foundation: purpose, public API, examples, consumers, gotchas. Cheapest viable doc; doesn't depend on tooling.
4. **Storybook stories-as-docs.** Frontend foundations: API table auto-generated from props; stories double as regression and visual tests. ([storybook.js.org](https://storybook.js.org/))
5. **CODEOWNERS.** Path → team mapping. Minimum viable ownership signal. Pairs with a per-foundation `OWNERS` block in the registry.

**Synthesis — fields to collect per foundation:**

`name · type · purpose · path · public API surface · invariants · owner team · consumers (fan-in) · depends-on (fan-out) · test coverage · status (active | deprecated | sunset) · last reviewed`

This is the row schema for `FOUNDATIONS.md`.

## 3. Health signals

Measurable indicators that a foundation has drifted away from "small, testable, decoupled, DRY."

### Coupling metrics

- **Afferent coupling (Ca).** Number of consumers depending on this foundation. Foundations *should* have **high Ca** — that's the point.
- **Efferent coupling (Ce).** Number of things this foundation depends on. Foundations should have **low Ce**.
- **Instability `I = Ce / (Ca + Ce)`.** Foundations want **low I** (stable). Rising I over time is a regression signal.

References: [Software package metrics — Wikipedia](https://en.wikipedia.org/wiki/Software_package_metrics), [Afferent / Efferent Coupling — coupling.dev](https://coupling.dev/posts/related-topics/afferent-and-efferent-coupling/), [Efferent coupling — Wikipedia](https://en.wikipedia.org/wiki/Efferent_coupling).

### Not all dependency edges are the same edge (added 2026-08-02)

Ca above treats every incoming dependency as one unit. The **key class detection** literature — a line running from Zaidman & Demeyer (2008) through Şora (2019) and the ranking-aggregation work since — converged on two positions that the plain-Ca framing above misses:

- **Importance is a graph-centrality property.** These methods rank classes with PageRank, LeaderRank, or Markov-chain rank aggregation over the class-collaboration graph, not with raw counts and not with directory or filename conventions. No method in this literature uses filenames — the premise of the field is that naming is precisely the signal that fails in the codebases most in need of analysis.
- **Edge types carry different weights.** Inheritance, instantiation, return-type, and method-call edges are weighted separately, because treating them uniformly demonstrably loses architecturally significant classes ([Structure Entropy Weighted LeaderRank](https://www.hindawi.com/journals/mpe/2020/9234042/)).

The second point has a direct consequence for detection. A subclass declaration is a far stronger claim than an import: the subclass inherits the parent's whole contract, where an importer borrows one function. It also produces a specific and predictable miss — **the layer foundation.** A `BasePresenter` inherited by twelve presenters, or a `BaseDao` by fifteen DAOs, has cross-feature spread of exactly 1 by construction, since its consumers all live in the one directory whose shape it defines. Any filter that requires spread ≥ 2 deletes it before scoring, and it is precisely the class an agent most needs to know about.

**Repokit's response (implemented 2026-08-02, unvalidated):** count subclass declarations as a separate signal, fold it in at 2× weight (`reach = fan_in + 2 × subclass_count`), and demote the spread requirement from a hard gate to a score penalty plus an explicit exemption at `subclass_count >= 5`. Filename conventions (`base.*`, `abstract.*`) are used only to break ties at the cut line, never to score. Layer foundations cap at Medium confidence so a human always confirms them. **(repokit hypothesis)** — the recall gain is untested, and the precision cost of admitting single-layer candidates is unmeasured.

Supporting argument from an adjacent field: retrieval work on repository-level generation finds that *"failing to retrieve true dependencies is far more damaging than including some irrelevant context"* ([arXiv:2602.11671](https://arxiv.org/pdf/2602.11671)), and reports that similarity-based retrieval performs worst specifically on **class** dependencies. A spread filter is a precision filter on a task where the evidence favors recall.

### Size and complexity

- **God class:** ~500 LOC and/or 20+ public methods is a common threshold.
- **Cyclomatic complexity** per public method.
- **Public-API breadth:** number of exported symbols — a foundation that exports everything has no encapsulation.

### Code smells (Fowler / industry catalogues)

- **Shotgun surgery** — one logical change requires touching N call sites. Sign of a leaky abstraction. ([luzkan smells catalog](https://luzkan.github.io/smells/shotgun-surgery/))
- **Feature envy** — methods on the foundation manipulate consumer-side data more than their own.
- **Divergent change** — one foundation changes for many unrelated reasons (low cohesion).
- **Primitive obsession** — public API uses primitives where a value object would serve.

### The "wrong abstraction" signal (Sandi Metz)

Param count and conditional count growing over time on a single function indicates the abstraction *guessed wrong* about its callers' needs. Metz's prescription: *prefer duplication over the wrong abstraction*; inline it back into callers and re-extract once the real shape is visible. ([sandimetz.com — The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction))

### Test and review hygiene

- **Untested public surface** — public method with zero referencing test files.
- **Stale review** — last review > N days, `git log` shows touches but no review entry.

### Deprecation drift

- **Ca trending toward zero** — consumers are migrating away. Candidate for sunset. ([Heroku — Sunsetting and Deprecation](https://blog.heroku.com/sunsetting-and-deprecation), [Mastercard Client Library Deprecation Policy](https://github.com/Mastercard/.github/blob/main/CLIENT_LIBRARY_DEPRECATION_POLICY.md))

### Ranking tools, and why repokit doesn't wrap one (resolved 2026-08-02)

The centrality ranking described above ships in production today: **aider** builds a tree-sitter symbol graph and ranks files with PageRank (`aider --show-repo-map` prints it and exits), and **RepoMapper** ([MIT](https://github.com/pdavis68/RepoMapper)) extracts that as a standalone tool with an MCP server mode. PageRank would surface a layer foundation for free — rank flows from twelve dependents regardless of which folder they occupy.

Repokit uses neither as a dependency. Three reasons, in order of weight:

1. **It answers a different question.** Aider's map decides *what goes in the prompt right now*: token-budgeted, personalized to chat context, output as a rendered signature tree. A foundation registry needs a stable ranking plus per-file evidence a human can check. Everything downstream of the rank — churn, cross-feature spread, consumer sets for conformance counting, hotspot/pretender classification — is absent from the map. Notably aider has **no stability signal at all**, so a hotspot and a healthy foundation rank identically.
2. **The dependency cost breaches a standing constraint.** Wrapping means the *consuming* project needs Python plus networkx, tiktoken, grep-ast, and compiled tree-sitter grammars — or an MCP server registered separately on three platforms. Repokit's detection is Markdown instructing an agent to run `grep` and `git log`: zero install, identical behavior across Claude, Antigravity, and Copilot.
3. **RepoMapper specifically is a single-maintainer port** (190 stars, no substantive commit since 2025-09; the later commits are a LICENSE file and a badge). Upstream aider is the better wrap target if one is ever wanted.

**Sanctioned use: opportunistic cross-check, never a dependency.** If `aider` happens to be on `PATH`, a deep scan may run `aider --show-repo-map` and *reconcile* its top-N against dockit's own — two independent rankings disagreeing is a useful blindspot signal, and set membership suffices, so nothing needs parsing for numbers. Degrades silently to nothing when absent.

**Left open:** implementing PageRank directly is ~30 lines of stdlib power iteration over import edges dockit already greps — no networkx, no tree-sitter, no tokenizer. Whether that counts as the retrieval layer repokit has committed not to build is genuinely unclear: dockit already ships a bespoke scoring formula, and this would replace a homegrown heuristic with a better-studied one for the same job. The distinction that seems to hold is **retrieval** (serving context per query) versus **ranking** (one-time doc generation) — but it has not been written into the charter's out-of-scope list, and it will come up again.

## 4. Ownership

Foundations without a named owner rot. The pattern that scales:

- **Team Topologies model.** A *Platform team* owns the foundation; *Stream-aligned teams* consume it self-service. ([teamtopologies.com](https://teamtopologies.com/key-concepts), [Fowler](https://martinfowler.com/bliki/TeamTopologies.html), [Atlassian summary](https://www.atlassian.com/devops/frameworks/team-topologies))
- **Backstage `spec.owner`** operationalises this: every component has exactly one owning team.
- **CODEOWNERS** is the minimum viable shadow of the same idea — enforced by GitHub at PR time.

**Antipattern:** "shared ownership" with no named team. Translates to no ownership in practice.

The split keeps each tool focused: dockit *describes*, auditor *detects*, modernizer *plans the fix*, agentkit *equips agents to work on it*.

## 6. Agent grouping — how to cluster foundations into agents

A foundation is a *row* in the registry. An *agent* is the unit of expertise generated by agentkit. The question of "one agent per foundation, or one agent per cluster?" turns out to have a non-obvious answer.

### The naïve mapping (rejected)

The first instinct is **one agent per foundation row**. It's clean, it's symmetric, and it makes per-row maintenance ownership obvious.

In practice it produces too many narrow specialists. Most non-trivial features touch more than one foundation — a "user can sign in with SSO" feature touches `core.auth` (the protocol), `core.permissions` (what the user can do once signed in), and `core.session` (state). With three agents, the human (or coordinating LLM) has to consult all three, reconcile their advice, and remember to update each one's owned doc. Three places where drift can leak in. Three contexts to switch between. The coordination cost is paid every feature, forever.

### The principle: Common Closure (CCP)

Robert C. Martin's **Common Closure Principle**, originally about Java packages, applies cleanly to agents: *"Classes that change for the same reason should be packaged together. Classes that change for different reasons should be in different packages."* ([Clean Architecture, Ch. 13](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html); [DZone summary](https://dzone.com/articles/the-common-closure-principle))

Translated: **agents should be grouped by what changes together, not by what's named alike.**

This is the package-level analogue of the Single Responsibility Principle: a package (or agent) has one *axis* of change, not necessarily one *responsibility*.

### Detecting change-coupling

The empirical signal is **logical (or change) coupling**: which files have historically been modified in the same commits. Adam Tornhill's [*Software Design X-Rays*](https://pragprog.com/titles/atevol/software-design-x-rays/) (Pragmatic Bookshelf) is the canonical reference; the underlying analysis powers tools like [CodeScene](https://codescene.com/). The key insight: high *temporal* coupling (co-change) often diverges from high *structural* coupling (imports), and the temporal signal is a stronger predictor of where refactoring should happen.

For agentkit specifically, the relevant computation per foundation pair `(A, B)`:

```
git log --name-only --since=12.months -- <pathA> <pathB> \
  | awk '/^commit /{c=$2} $0==pathA{a[c]=1} $0==pathB{b[c]=1} END{
    n=0; for(k in a) if(b[k]) n++; print n
  }'
```

If `n ≥ 3` over 12 months, the foundations are change-coupled. (In practice, agentkit doesn't run this analysis during planning — too expensive — but uses it as a tiebreaker when grouping is ambiguous.)

Cheaper proxies that correlate with change-coupling:

- **Shared consumers** — feature folders that import one foundation tend to import the other. Updating either to satisfy a new feature requires touching both.
- **Joint invariants** — an invariant in foundation A references foundation B (e.g., *"every auth token must be issued by core.auth and validated by core.permissions"*). The invariant is itself a contract that spans both.
- **Same directory tree** — `core/auth/`, `core/auth/permissions/`. The team already grouped them spatially, which usually reflects how features land.
- **Same domain** — auth, data layer, notifications. Weakest signal alone — but combined with one of the above, it's reliable.

### Counter-signals (when to keep separate)

Splitting foundations into separate agents is justified only when one of these holds:

- **Distinct teams** — `Owner` field differs. A platform-team foundation and a feature-team foundation shouldn't share an agent even if they're functionally related; ownership is itself an axis of change.
- **Mutually orthogonal invariants** — you can't construct a feature that would touch both. They aren't change-coupled because they aren't *anything*-coupled.
- **Hotspot/healthy mismatch** — one foundation is a `health: hotspot` (high churn), the others are `healthy`. The hotspot's churn would force constant re-syncing of an agent that mostly didn't need it.
- **Size budget exceeded** — the merged agent would blow past the practical context budget (~10,000 chars body in agentkit's case). At that point, split on the weakest change-coupling boundary.

### Antipatterns named in prior art

The same intuition appears under different names in the code-smell literature:

- **Shotgun surgery** ([Fowler](https://refactoring.guru/smells/shotgun-surgery), [luzkan smells catalog](https://luzkan.github.io/smells/shotgun-surgery/)) — one logical change requires touching N call sites. The agent equivalent: one feature requires consulting N agents and reconciling their answers. Same root cause: cohesion failure.
- **Divergent change** ([refactoring.guru](https://refactoring.guru/smells/divergent-change)) — one module changes for many unrelated reasons. The agent equivalent: an agent that owns foundations belonging to different change axes.

CCP rules out divergent change by construction; the change-coupling test rules out shotgun surgery.

### The operational test

Before splitting two foundations into separate agents, the planner asks:

> *"If a feature came in that needed to touch both, would I be OK with the human (or LLM) consulting two agents and merging their advice — every time, for the life of this project?"*

If the answer is "no," merge. The test is asymmetric on purpose: the cost of over-splitting is paid forever (per feature), while the cost of over-merging is paid once (the agent is slightly broader than ideal).

### Why the naïve mapping persists despite being wrong

It's tempting to map 1:1 because:

1. **Symmetry feels clean.** One row in FOUNDATIONS.md ↔ one agent file. Easy to explain.
2. **Ownership is unambiguous.** No question who updates what when a foundation changes.
3. **The cost is invisible.** Coordination overhead per feature doesn't show up in any individual interaction; it accumulates.

The 1:1 mapping is *valid* as a fallback — when foundations genuinely don't change-couple, it produces minimal-coordination agents. It's the wrong *default*.

### Implication for FOUNDATIONS.md schema

The change-coupling lens implies one new piece of metadata is worth capturing per row, even if optional: a **cluster hint**. Either:

- An explicit `cluster: <name>` field the maintainer can set, OR
- An implicit signal — multiple foundations with the same `cluster` tag get folded into one agent unless agentkit detects a counter-signal.

This is not yet implemented; the current AGENT-SIZING heuristic uses inferred signals. A `cluster` field would make the grouping deterministic and let teams override it explicitly.

### Grouping pressure from the other direction (added 2026-08-02)

Everything above answers "which foundations belong in one agent." A second force pushes on the same decision from outside the registry: **coverage.** Once a tool reports which directories no agent claims, the cheapest way to clear the report is to widen the nearest agent — and in the one field case observed, that meant expanding a single agent across four architectural layers at once.

The Common Closure Principle already argues against this (those layers don't change for the same reason), but a coverage number is a more legible target than a principle, so the principle loses unless something enforces it. Repokit's answer, shipped 2026-08-02 and unvalidated: classify the uncovered directory's architectural layer against the candidate agent's existing layers, and propose a *new* agent rather than a fold when they differ and fewer than two change-coupling signals connect them — with the § 6 ceilings still binding above coverage. An uncovered directory the user has seen and accepted beats a covered one whose owner can't advise on it.

**(repokit hypothesis, n=1.)** The behavioral claim — that coverage reporting induces scope inflation — rests on a single observation, and the guardrail's effect is unmeasured.

## 7. Open questions

- **Granularity.** Is one foundation = one directory? One module? One class? Likely a mix; the registry should allow path *or* symbol scoping. **Partially answered 2026-08-02:** a class is a legitimate foundation, and the layer-foundation category scopes by symbol — `subclass_count` is a symbol-level signal and the row records the consuming layer. What remains open is whether symbol-scoped rows need a distinct schema or just a `scope:` field on the existing one, and how sync detects the rename of a symbol as opposed to a path.
- **Thresholds.** LOC, method-count, Ca/Ce thresholds are language- and project-dependent. Where do defaults live — modernizer's language reference files, or a per-project `foundations.config`?
- **Detection without metrics tooling.** Many projects don't have SonarQube. How much can the auditor do with `git`, `grep`, and language-native tools alone? **Partially answered 2026-08-02:** further than assumed — subclass counting is a grep, and the whole four-signal score runs on `grep` + `git log`. The ceiling is real graph centrality, which needs a symbol graph and therefore compiled tree-sitter grammars; that's the line where the constraint bites, and § 3 records why repokit stops short of crossing it. Still open: whether ~30 lines of stdlib PageRank over grep-derived edges gets most of the benefit without the dependency.
- **Lifecycle states.** Backstage uses `experimental | production | deprecated`. Do we need a fourth state for "under refactor"?
- **Cross-plugin contract.** Auditor (repokit) emits signals; modernizer (tikkit) consumes them. What's the on-disk format — a JSON file in `.backlog/`? Backlog entries with a structured suffix?
- **Cluster field in FOUNDATIONS.md.** Section 6 implies an optional `cluster: <name>` field per row would let teams override agentkit's grouping deterministically. Should dockit's template add it? When does the inferred-grouping path stop being good enough?
- **Change-coupling computation cost.** The git-log analysis in § 6 is the strongest grouping signal but the most expensive. Is there a lightweight pre-computed form (e.g., a `.dockit/coupling.json` cache refreshed during `/dockit sync`) that agentkit could read instead of recomputing during planning?
