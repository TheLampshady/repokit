# Drift Detection for Agent Context — Research

**Date:** 2026-08-01
**Original request:** Research drift detection — mechanics and tooling examples — for agent context files (AGENTS.md, CLAUDE.md, GEMINI.md, Cursor rules), the docs repokit generates, and subagent/skill definitions.
**Goal:** Specify how repokit's sync/check/audit loop should detect context drift: which detection mechanics are proven, what tooling already exists, and where the open niches are.
**Note (2026-08-01, post-research):** `audit` has since been removed as a mode. Its deterministic reference checks moved into every `sync` (Layer 1 below, as this document recommends), and the whole-repo work that genuinely needs a slow pass became a `sync --deep` flag. Read "audit" below as "the deep pass" — no finding or recommendation changes.
**Constraints:** Anything recommended must be open source and free. Evidence bar: practitioner consensus, upgraded by benchmarks and skeptical reports wherever they exist.
**Provenance:** This document stands alone — it references no other document in this repository. External claims cite primary sources inline. Positions marked **(repokit hypothesis)** originated in project working discussions, not the literature; they are hypotheses repokit intends to validate by experiment, and evidence cited near them is supporting context, not proof.

## Executive summary

**Revised 2026-08-04 (third entry)** — **`Last reviewed` dates are removed from FOUNDATIONS.md**, along with the 90-day cadence and agentkit's stale-review drift category. Owner attribution — the part with evidence behind it — stays. Reviews are now event-triggered (you're in the code anyway) and age is derived from git on demand, never stamped. Full reasoning under layer 5, including the uncovered gap this leaves.

**Revised 2026-08-04 (second entry)** — **dockit's `check` mode is removed and no gate replaces it**, resolving a standing contradiction with layer 5's warn-don't-block finding. The generalisable reason: an exit code produced by a language model is not a gate, because it fails open silently behind a binary interface. Recorded in full under layer 5, including the honest cost — `/repokit status` now reports doc *recency*, not a content verdict.

**Revised 2026-08-04** — **layer 2 (evidence recounts / stored predicates) is removed and will not be built.** A conformance ratio measures obedience to a directive, not the truth of a claim, and only descriptive claims can be falsified at all; enforcement is commodity and belongs in a linter. This narrows the document's honest scope: drift detection targets *what a doc names*, not *how well a rule is followed*. Replacement hypothesis is the **named anti-pattern**. New sources: Treude & Baltes (context rot, measured), the architecture-conformance tool class, Factory.ai. The remaining layers are unchanged.

**What to do:** build repokit's sync loop as three detection layers — a deterministic five-check core on every sync (paths resolve, commands exist, claims match config, cross-file agreement, both directions), diff-scoped LLM claim-verification per change, and nag-don't-block process enforcement — and claim the two niches nobody occupies: verifying agent *descriptions* against the code they describe, and measuring drift rates at all.

- **The problem is real and measured:** drift is overwhelmingly silent omission (only 13–20% of code changes touch adjacent docs — [Fluri et al. 2009](https://link.springer.com/article/10.1007/s11219-009-9075-x)), and agents obey stale claims with full compliance ([ETH Zurich](https://www.sri.inf.ethz.ch/publications/gloaguen2026agentsmd); [Packmind](https://packmind.com/evaluate-context-ai-coding-agent/)) — a wrong claim is an obeyed error, not noise. Independently measured in AI config files specifically: **23% of 356 repositories carried stale code references**, 64% confirmed genuine ([Treude & Baltes](https://arxiv.org/html/2606.09090)).
- **Deterministic checks are proven mechanics, unproven impact:** six near-identical MIT linters converged on the same five checks; cheap and sub-second, but zero adoption/impact evidence. Treat the checks as the standard, not any one tool.
- **LLM auditing works in principle, unmeasured in practice:** two converged shapes (diff-scoped ~$0.50–2/run; claim-extraction-then-verification), backed by the verification-easier-than-generation asymmetry — but no published false-positive/negative rates anywhere (absence claim).
- **Process mechanisms rot without an owner:** freshness dates rubber-stamp and gates get bypassed; the fixes with evidence are owner-attributed stamps ([SWE at Google](https://abseil.io/resources/swe-book/html/ch10.html)) and warnings instead of blocks.
- **The maturity target exists:** OpenAI's Harness team runs background cleanup agents at 1M-line scale with a ~100-line AGENTS.md table of contents ([Lopopolo, Feb 2026](https://openai.com/index/harness-engineering/)) — self-reported, but the only account of drift maintenance as routine practice.
- **The open ground is repokit's:** description-vs-code sync and drift-rate telemetry have no public prior art (absence claims) — first-mover territory for agentkit and sync instrumentation.

## Key findings

### The failure mode, quantified

- **Drift is silent omission, not bad edits.** When comments do change, they co-change with code >90% of the time — but only 13–20% of code changes trigger any comment update at all ([Fluri/Würsch/Gall, Software Quality Journal 2009](https://link.springer.com/article/10.1007/s11219-009-9075-x) — old but canonical; corroborated at scale by [Wen et al., ICPC 2019](https://dl.acm.org/doi/abs/10.1109/ICPC.2019.00019), 1,500 Java systems). Follow-on work finds code-comment inconsistency measurably correlates with bug introduction ([arXiv 2409.10781](https://arxiv.org/pdf/2409.10781)).
- **Agents make stale context strictly worse than stale docs.** Context-file instructions are followed "rigorously but counterproductively" even when wrong ([ETH Zurich, arXiv 2602.11988](https://arxiv.org/abs/2602.11988)); field audits show agents obeying outdated claims with full compliance — Jest-vs-Vitest, stale Node versions, Postgres→MySQL migration leftovers ([Packmind](https://packmind.com/evaluate-context-ai-coding-agent/), Feb 2026 — vendor blog, anecdotal base of "dozens of real CLAUDE.md files").
- **Nobody measures drift rates.** No quantitative before/after or drift-velocity study exists anywhere in the agent-context space (absence confirmed by searching across all three research passes). The evidence base is converging anecdotes plus the old SE research above.

### Layer 1 — Deterministic linters for agent context files

A young, crowded niche of free MIT-licensed CLIs, all deterministic-first, none with independent adoption or impact evidence (all claims below are author-documented mechanics, fetched directly):

| Tool | Paths exist | Commands exist | Claims vs config | Cross-file consistency | Freshness | LLM layer |
|---|---|---|---|---|---|---|
| [agents-lint](https://github.com/giacomo/agents-lint) | ✓ | ✓ (package.json) | ✓ (framework patterns, e.g. `ReactDOM.render()` flagged as outdated) | ✓ (AGENTS.md vs CLAUDE.md path asymmetry, npm-vs-yarn conflicts) | proxy (old year refs) | — |
| [AgentLint](https://github.com/0xmariowu/AgentLint) | ✓ | ✓ | partial | ✓ | ✓ | opt-in (7 of 58 checks; incl. mining session logs for ignored rules) |
| [agentlinter](https://github.com/seojoonkim/agentlinter) | ✓ | ✓ (both directions — also flags *undocumented* scripts) | — | ✓ | partial | — |
| [cclint](https://github.com/felixgeelhaar/cclint) | ✓ (`@import` resolution) | — | — | monorepo duplicate content | — | explain-only |
| [context-drift](https://github.com/geekiyer/context-drift) | ✓ | ✓ | ✓ (dependency versions) | ✓ | — | ✓ (MCP prose-claim check via host model) |

- **The mechanics catalog is stable across tools:** (a) referenced paths resolve, (b) named commands/scripts exist, (c) claims match config, (d) cross-file agreement, (e) freshness signals — all sub-second, zero-network, no API key. The differentiators are thin; the niche is six implementations of the same five checks.
- **The unique mechanics worth noting:** AgentLint's session-log mining (evidence a rule is being *ignored*, not just stale) and agentlinter's reverse check (scripts that exist but are undocumented — drift by omission, the statistically dominant kind).
- **Zero evidence any of them improves agent outcomes.** The one tool publishing numbers ([ctxlint](https://dev.to/vamshidhar_reddy_392c2302/i-built-a-linter-that-proves-74-of-your-agentsmd-is-wasting-your-ai-agents-time-46an): "74% waste, 91% precision") is self-reported theoretical token math, not behavior impact — low confidence.

### Layer 2 — LLM-judged auditing

- **Two converged mechanics.** (1) *Diff-scoped checks*: analyze recent changes, find affected docs, LLM flags factual contradictions — [driftcheck](https://github.com/deichrenner/driftcheck) (MIT, pre-push hook, works with local models via Ollama) and the Claude-Code-in-GitHub-Actions pattern at ~$0.50–2.00 per run, ~$10–40/day on a 20-PR/day repo ([Dosu, Mar 2026](https://dosu.dev/blog/how-to-catch-documentation-drift-claude-code-github-actions) — vendor blog with honest caveats: "catches what's explicit, misses what's implied"). (2) *Claim-extraction-then-verification*: extract 5–10 verifiable claims per doc, verify each against code, emit a claim/result table (the docs-auditor skill pattern, [LobeHub listing](https://lobehub.com/ja/skills/nimblebraininc-skills-docs-auditor)).
- **The full-repo LLM auditor exists and is open source.** [Packmind context-evaluator](https://github.com/PackmindHub/context-evaluator) (MIT) drives your already-installed agent CLI (Claude Code, Cursor, Copilot, Codex) through ~17 named evaluators — Command Completeness, Contradictory Instructions, Context Gaps, Outdated Documentation — and scores the repo. Cost rides on your existing subscription. It is the OSS funnel for a commercial product; its evidence base is anecdotal.
- **The principle is sound; the measurements don't exist.** Verification being easier than generation is well-established ([Wei, asymmetry of verification](https://www.jasonwei.net/blog/asymmetry-of-verification-and-verifiers-law)), and *self*-verification is known-weak — improving generation doesn't improve self-checking ([arXiv 2602.07594](https://arxiv.org/abs/2602.07594)), which argues for cross-agent verification designs. But **no published study measures false-positive/false-negative rates of LLM doc audits against labeled ground truth** (absence claim — confirmed by targeted searching) — every "conservative, low false positives" claim in this space is asserted, not proven.
- **Documented failure modes of continuous-audit loops:** hallucinated fixes passing review ("laundered misinformation"), PR volume exceeding value on small doc surfaces, and oscillation between equivalent rewordings ("drift-loop churn") ([AgentPatterns — continuous documentation](https://www.agentpatterns.ai/workflows/continuous-documentation/), reviewed Jul 2026; publisher unverified). The pattern "works best when drift is frequent enough that detection — not correction — is the bottleneck."
- **The strongest operational account:** OpenAI's Harness team (~1M lines, ~1,500 PRs, 3 engineers) runs "background cleanup agents: periodic agents scan for stale documentation, constraint violations, and pattern deviations, opening small refactoring PRs," mostly auto-merged; "repository knowledge is treated as a product: versioned, maintained, kept fresh by agents." Their AGENTS.md is held to ~100 lines as a table-of-contents with progressive disclosure ([Lopopolo, "Harness engineering," Feb 2026](https://openai.com/index/harness-engineering/)). First-party, single team, no counterfactual — but the only published account of drift maintenance as routine, working practice.

### Layer 3 — Docs-as-code prior art (what transfers, what rots)

- **Deterministic coupling works and is the cheapest trick in the book.** [embedme](https://github.com/zakhenry/embedme) (MIT): code blocks declare a source path, the tool injects the real code, `--verify` fails CI when doc and source diverge. Swimm industrialized the same idea with a weighted signal "histogram" that auto-patches trivial drift and punts complex changes to humans ([Swimm auto-sync](https://swimm.io/blog/how-does-swimm-s-auto-sync-feature-work), 2021). The principle both encode: **make the source the single source of truth and check the copy mechanically** — never sync prose by hand.
- **Executable docs verify commands the way tests verify code.** [Runme](https://docs.runme.dev/getting-started/cli/) (Apache-2.0) executes the shell blocks in Markdown in CI ("keep docs from bitrot"); doctest/rustdoc remain the highest-reliability form — but all of these verify *code/command snippets*, not prose claims.
- **Freshness metadata rots unless a named owner is attached.** Google's g3doc practice — `freshness: { owner: 'username', reviewed: 'date' }` with automated nagging — reports that attaching an *owner* to the date is what drove adoption ([SWE at Google, ch.10](https://abseil.io/resources/swe-book/html/ch10.html)); Microsoft's `ms.date` tracks edit-date, not verified-date — exactly the rubber-stamp failure. Reminder-only tools (docdecay et al.) keep appearing and fading.
- **PR gates should nag, not block.** The standard danger.js recipe warns (not fails) when `src/**` changed but `docs/**` didn't ([danger.js](https://danger.systems/js/guides/the_dangerfile.html)); hard gates get institutionalized bypasses fast (`[changelog skip]` tags, ruleset bypass lists). Ecosystem consensus by revealed preference: warning > blocking.
- **Cautionary market signal:** Swimm — the best-funded doc-sync company — could not sustain snippet-sync as a standalone product and pivoted to feeding verified context to AI agents ([Swimm 2.0](https://swimm.io/blog/swimm-2-0-the-understanding-platform-for-ai-modernization), 2025–26). The demand moved to exactly the "docs as agent context" framing; snippet-level sync alone was not the durable value.

### Subagent and skill definitions

- **Descriptions measurably drive routing, and the official tooling tests them against *queries*.** Anthropic's skill-creator v2 ([anthropics/skills](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), open source) generates ~20 should/shouldn't-trigger queries with near-misses, runs an automated optimization loop with train/test split, and selects descriptions by held-out trigger rate; Anthropic reports improvement on 5 of 6 internal skills, and one independent practitioner measured 81 → 97.5 across four evals ([O'Brien, Mar 2026](https://dev.to/debs_obrien/i-used-skill-creator-v2-to-improve-one-of-my-agent-skills-in-vs-code-fhd)).
- **Definitions-as-build-outputs is the working sync model.** [wshobson/agents](https://github.com/wshobson/agents) (38.4k stars, MIT) keeps a single source-of-truth and transpiles to Claude Code, Codex, Cursor, Gemini CLI, and Copilot formats via `make generate`, with `make validate` (structure) and `make garden` (drift/dead-link detection). Hand-editing generated artifacts is the anti-pattern.
- **Nobody verifies descriptions against code.** No tool or documented practice checks whether an agent/skill description still matches the codebase it describes (absence confirmed by targeted searching). Skill-audit tools check structure and security, not code-sync. Direct evidence that stale descriptions cause mis-routing also doesn't exist — only the well-evidenced adjacent chain (descriptions are the sole routing signal; trigger rates are sensitive to wording).
- **Don't conflate:** academic work on *goal drift* in coding agents (runtime behavior drifting mid-task) is a different problem from context/definition staleness.

### What vendors ship

Generation, not detection. Anthropic ships `/init` plus manual guidance ("treat CLAUDE.md like code... prune it regularly" — [best practices](https://code.claude.com/docs/en/best-practices)); OpenAI's Codex guidance is reactive ("when Codex makes the same mistake twice... update AGENTS.md"); Cursor ships nothing, and community guidance warns stale rule globs silently stop firing after folder renames ([Atlan](https://blog.atlan.com/engineering/cursor-rules/)). The drift-detection layer is entirely third-party.

## How this applies to repokit

### The layered sync architecture **(repokit hypothesis — the design this research supports)**

Repokit's context-in-sync premise sits on the best-evidenced gap in the field: drift is the dominant, measured failure mode; detection tooling is young, fragmented, and evidence-free; and the deterministic mechanics are proven, cheap, and unclaimed as an integrated loop. The proposed structure — a hypothesis to build and validate, not established practice:

1. **Deterministic core, every sync (free, sub-second).** The five-check catalog the linter niche converged on: referenced paths resolve; named commands exist in Makefile/package.json/pyproject; claims match config (dependency versions, tool names); cross-file agreement (AGENTS.md vs CLAUDE.md vs GEMINI.md); both directions — including agentlinter's reverse check for *undocumented* capabilities, since silent omission is the statistically dominant drift ([Fluri et al.](https://link.springer.com/article/10.1007/s11219-009-9075-x)). Rather than depending on any single early-stage linter, treat the mechanics as the standard: they are all reimplementations of the same five checks.
2. ~~**Evidence recounts for mined conventions (deterministic, every sync).**~~ Where repokit emits a convention with a conformance label ("11/13 handlers conform"), re-run the count on sync; decay (11/13 → 6/13) or a dead exemplar path flags the rule **(repokit hypothesis — this mechanic has no public prior art; it is the agent-context analogue of embedme's `--verify`)**.

   > **Refinement (2026-08-01, working discussion):** the conformance label should ship as a **stored predicate, not visible prose**. The generating pass writes the check it used — a literal shell command plus expected result — into a comment adjacent to the rule; sync re-runs that exact command rather than re-deriving the count from a fresh analysis. Two reasons. First, **stability**: a re-derived count depends on the analysis pass looking in the same place twice, so an agent that scopes its scan differently reports drift that isn't there — the dominant false-positive risk in an LLM-driven recount. Re-running a fixed command returns the same answer every time, which is what makes this layer belong in the deterministic tier at all rather than the LLM tier. Second, **cost on the read side**: printing "11/13 handlers conform" in the rendered rule taxes every agent that reads the doc to follow the rule, for information that only matters at verification time. The visible line stays a bare instruction; the machinery hides. Corollary for the negative-constraint problem: a prohibition is only admissible if it ships with a predicate, since context alone is the weak enforcement path and the predicate is what backs it up **(repokit hypothesis — the stored-predicate form is untested; the underlying recount mechanic is the one cited above)**.

   > **⛔ Layer 2 removed entirely, 2026-08-04.** Neither the recount nor the stored-predicate form ships. The 2026-08-01 refinement above was answering the wrong question well: it optimised *how* to re-measure without establishing *whether* re-measuring belongs in a context tool. Three findings, in order of force.
   >
   > **(a) The predicate never reached a reader who could act on it.** Agentkit strips `dockit:` comments when building agent hot memory, by explicit design. So the predicate ran at sync time, in a report, to a human — and the claim that it "carries the enforcement the wording can't" (the negative-constraint corollary above) was structurally false the whole time it stood. See the resolved question in [choice-over-overview-research.md § Open questions](./choice-over-overview-research.md#open-questions).
   >
   > **(b) A conformance ratio is not a drift signal, because a directive can't be falsified by disobedience.** This is the load-bearing correction, and it splits this document's subject in two. *Descriptive* claims — "auth lives in `src/auth/`", "`SearchClient` has 11 consumers" — become **false** when the code moves; verifying them is drift detection and stays in scope. *Prescriptive* rules — "all config comes from `Settings`" — are not falsified by three violating files; they are *disobeyed*. Measuring that is a compliance audit. Layer 2 was the only layer aimed at prescriptive content, and it was measuring obedience while the rest of the architecture measures truth.
   >
   > **(c) Commodity.** [ArchUnit](https://www.archunit.org/), [import-linter](https://import-linter.readthedocs.io/), and [dependency-cruiser](https://github.com/sverweij/dependency-cruiser) do conformance enforcement on the hot path — pre-commit, CI, build failure — where it works. [Factory.ai](https://factory.ai/news/using-linters-to-direct-agents) states the resulting split cleanly: prose carries intent, the linter carries the guarantee, and the guarantee lives *in the linter*. The charter's wrap-or-recommend rule applies.
   >
   > **Refined 2026-08-04 (same day) — one narrow case where counting sites is legitimate.** `/repokit status` reports pending sites for `intended` entries: *"`core.settings` — 15 sites, grouped by directory, repair: add a field to Settings."* That is a "how many places don't follow this rule" count, which the removal above appears to forbid, so the distinguishing line matters and it is **consent, not mechanism**. Marking something `intended` declares that the code hasn't caught up; a list of what's left answers the question the marker asks. The identical grep against an *unmarked* rule audits a claim nobody invited, which is the treadmill. Also load-bearing: it is a **count of named sites, never a ratio**, it appears only where the user asked (`status`, never a sync report), it has no trend or history, and a grep is stated as a lower bound so it plans a migration rather than backing a compliance claim.
   >
   > This is the useful generalisation of the whole layer-2 episode: the defect was never *reading code and comparing it to a rule*. It was doing so **unbidden, as a recurring verdict on the doc**. Same grep, different subject and different trigger, different feature.
   >
   > **What replaced it.** The pattern the command encoded — which specific accessor or import the rule displaces — is now written into the visible line as a **named anti-pattern** plus a repair. That moves the one actionable fact from a comment no agent read into hot context, and `--deep` verifies the named pattern still resolves as an ordinary reference check (layer 1's job). Removal of a mined rule is now triggered only by *the code it governs disappearing* — never by falling conformance.
   >
   > **Corroboration that the underlying problem is real, and what shape it has.** [Treude & Baltes](https://arxiv.org/html/2606.09090) measured context rot across 612 config files in 356 repos: **23.0% carried stale code references, 64% confirmed genuine.** Note what they measured — *does the element this file names still exist* — which is exactly layer 1, and they recommend reusing existing documentation-consistency tooling rather than new mechanisms. The evidence supports the descriptive checks and says nothing for the conformance one.
3. **LLM claim-verification, diff-scoped (per sync/PR, costed).** The converged shape: scope to changed files, extract claims, verify against code, cross-agent rather than self-verifying ([arXiv 2602.07594](https://arxiv.org/abs/2602.07594)). Budget expectation from the field: ~$0.50–2 per run ([Dosu](https://dosu.dev/blog/how-to-catch-documentation-drift-claude-code-github-actions)). Tuned conservative — and honestly labeled as unproven, since no FP/FN benchmarks exist anywhere.
4. **Agent-description sync — repokit's empty-niche opportunity.** agentkit descriptions/instructions verified against the foundations and code they describe has *no public prior art*. The adjacent proven pieces: definitions-as-generated-artifacts (wshobson's model — regenerate, don't hand-fix) and query-based trigger evals (skill-creator v2) for the routing side. Combining code-sync verification with trigger-eval verification would be novel territory **(repokit hypothesis)**.
5. **Process layer: nag, don't block, and name an owner.** Two mechanisms, both evidenced, neither yet built:
   - **A trigger that fires at change time, warning rather than failing.** The danger.js lesson is that hard gates breed institutionalized bypasses, so the check must warn ([danger.js](https://danger.systems/js/guides/the_dangerfile.html)). Two delivery shapes have prior art: a **git hook** — driftcheck runs exactly this as a pre-push hook, against local models to keep it free — or a **subagent** invoked at completion checkpoints. Repokit currently ships no hooks, so either is net-new surface; `hooks.json` (Antigravity) and `hooks/hooks.json` (Claude) are the distribution points if the hook shape wins **(repokit hypothesis — the warn-don't-block principle is evidenced, the repokit-shaped delivery is not)**.
   - ~~**Owner-attributed freshness stamps, written by dockit.**~~ A date alone rubber-stamps; attaching an *owner* is the one mitigation with documented adoption impact ([SWE at Google](https://abseil.io/resources/swe-book/html/ch10.html)). dockit already writes `Last reviewed` into FOUNDATIONS.md catalog rows, so this is an extension of an existing field rather than new machinery.

     > **Amended 2026-08-04 — the stamp is removed; the owner stays.** `Last reviewed` is gone from the template, the samples, agentkit's maintenance triggers, and agentkit sync's drift categories (which drops from seven to six). The `Owner` column remains.
     >
     > This splits the cited finding in two, and only half of it survives. The evidenced part is **attribution** — naming who is responsible. The date was the part this document already knew rubber-stamps, and shipping it anyway produced exactly that: agentkit's guide instructed agents to "bump **Last reviewed**" when re-copying a canonical call site, which is an edit, not a verification. A field meant to assert *someone read the code and the invariants hold* was being set by touching a row.
     >
     > It also violated the charter directly: *"Measured from git history, never stamped into the doc — a written staleness date is itself a tombstone."* The rule pre-existed the field. **Third instance in this project of a doc-stated rule contradicted by the implementation** (after the negative-phrasing reversal and the `check`-vs-warn-don't-block gate), which is enough of a pattern to name: the contradictions all ran the same direction — a locally reasonable mechanism outliving a rule recorded elsewhere and never re-read.
     >
     > **What replaces it:** derive on demand (`git log -1 --format=%cr -- <path>`), which can't disagree with itself, plus an event trigger — validate invariants when you're working on the foundation anyway. Explicitly rejected as a substitute: reporting a git-derived age on every sync. That's the same calendar nag with a cleaner source, and the reason for removal was the nagging, not the storage format.
     >
     > **Cost:** nothing now prompts a review of a foundation nobody touches. A stable, correct, quietly-rotting foundation gets no attention until someone opens it. That is the gap the 90-day cadence existed to cover, and it is now uncovered by design — on the argument that a calendar prompt bought compliance theatre rather than review. Unmeasured either way.

   > **Note (2026-08-01):** an earlier draft attributed the change-time trigger to the `feedback-loop` agent. That was a category error — feedback-loop ran lint → format → typecheck → test and filed tickets for what it couldn't fix; it never inspected context for drift. The agent has since been removed from repokit, but the mechanism above was never its job, and the recommendation does not depend on it.

   > **Acted on 2026-08-04 — dockit's `check` mode is removed, and no gate replaces it.** This layer's warn-don't-block principle had been recorded as evidenced while dockit simultaneously shipped `check`: a read-only mode returning **exit 1 on stale docs**, documented for pre-commit and CI in a `GIT-HOOKS.md` guide (now deleted). The contradiction stood for as long as both documents did, which is the second instance in this project of a plausible local decision surviving because nobody re-read the corpus it contradicted.
   >
   > Three reasons for removal, and the first generalises beyond repokit:
   >
   > **(a) An LLM-produced exit code is not a gate.** `claude /dockit check` returns 0 or 1 according to a model's judgement about whether to exit non-zero. CI consumes that as a deterministic fact. The failure mode is silent fail-open — the gate passes a drifted repo and nobody learns it stopped working. This is worse than shipping no gate, because a gate that is believed is load-bearing. **Generalisation: any pipeline gate whose verdict comes from a model inherits the model's variance while presenting a binary interface.** Applies to hypothesis 3 (LLM claim-verification) if it is ever wired to fail a build rather than comment on a PR.
   >
   > **(b) Gating documentation inverts the working order.** Code changes, then docs follow. At commit time the docs are *supposed* to be briefly behind, so failing the commit penalises the only sequence available. The loop that works is change → sync → commit both together.
   >
   > **(c) `check`'s entire output was a redirect** — "documentation is stale, run sync" — making it a third read-only inspector alongside `/repokit status` (human-facing) and `sync --deep` (thorough), distinguished only by the exit code. Remove the gating and nothing was left.
   >
   > **The cost, recorded honestly:** `/repokit status` lost its doc-drift verdict and now reports a *recency* signal — code changed after docs — explicitly labelled "may be behind" rather than "stale", plus any open findings from the last sync report. That is weaker, and the weakening is real: nothing read-only now inspects doc *content*. A content answer requires `sync --deep`, which writes. Whether a recency proxy is enough to keep the dashboard row worth reading is unmeasured.
   >
   > **Still unbuilt, and now the only automation candidate left:** the warn-don't-block trigger above. Note it must warn *without* an exit code to be consistent with (a) — a post-commit or pre-push reminder that sync is due, not a check that fails.

### Secondary implications

- **Instrument the loop — repokit could produce the field's first drift-rate data** **(repokit hypothesis)**. Nobody measures how fast agent context rots or how many claims a sync pass corrects. Sync-mode telemetry (claims checked, claims failed, category, age) would be genuinely novel evidence, not just product surface.
- **The OpenAI Harness pattern is the maturity target:** periodic background cleanup at a cadence where most fixes auto-merge, with the always-loaded file held to ~100 lines as a table of contents ([Lopopolo](https://openai.com/index/harness-engineering/)). Repokit's sync mode is the plugin-shaped version of that practice.
- **Expect and design for the audit-loop failure modes:** hallucinated fixes surviving review, churn on small doc surfaces, reword oscillation ([AgentPatterns](https://www.agentpatterns.ai/workflows/continuous-documentation/)). Confirm-or-delete drafts and diff-scoped runs are the mitigations the field has converged on.

## Hypotheses to implement

The actionable roll-up of everything marked **(repokit hypothesis)** — each with the concrete change or experiment that would test it:

1. **Layered sync architecture** — implement the deterministic five-check core in repokit sync; test by seeding a repo with known drift (dead paths, renamed scripts, config mismatches) and measuring catch rate.
2. ~~**Evidence recounts for mined conventions**~~ — **withdrawn 2026-08-04, not implemented.** A conformance ratio measures obedience to a directive, not the truth of a claim, and enforcement is commodity ([ArchUnit](https://www.archunit.org/), [import-linter](https://import-linter.readthedocs.io/), [dependency-cruiser](https://github.com/sverweij/dependency-cruiser)); full reasoning in [the layered sync architecture](#the-layered-sync-architecture-repokit-hypothesis--the-design-this-research-supports), layer 2.

   **Replacement hypothesis — the named anti-pattern (added 2026-08-04).** A mined boundary rule carries the accessor or import it displaces, in the visible line, with a repair: *"all config comes from `Settings` — direct `os.environ` reads bypass validation and defaults; add a field to `Settings`."* The claim is that this beats the bare positive instruction on compliance, because an agent cannot recognise a violation it cannot name — and beats the predicate trivially, since the predicate was never in the agent's context at all. Test: same task, same repo, three arms — rule alone, rule + named anti-pattern + repair, and (as a floor) no rule. This is the A/B the retired predicate question should have been **(repokit hypothesis, unmeasured)**. Secondary test for layer 1: rename the anti-pattern's target and confirm `--deep` reports it as a stale reference.
3. **Description-vs-code sync (agentkit)** — verify agent descriptions against the foundations/code they describe on sync; test by aging a description past a real code change and confirming detection, then pair with a skill-creator-style trigger eval to measure whether the refresh changes routing.
4. **Drift-rate telemetry** — instrument sync to log claims checked/failed by category and age; success is the first real drift-rate dataset, publishable on its own.
5. **Diff-scoped LLM claim-verification** — add as a costed sync layer (~$0.50–2/run expectation); test against a small labeled set of true/false doc claims to produce the FP/FN numbers the field lacks.
6. **Trigger coverage gaps — drift measured against the code, not the catalog (added 2026-08-02).** Every check in 1–5 compares a claim against the thing it claims about. This one has no claim to check: it asks which parts of the codebase are covered by *no* agent's scope at all. Detection is a covered-set union over every agent's working directories and description globs, subtracted from the active source tree, plus two symbol-level probes — inheritance roots with ≥5 subclasses that no agent names, and single-file scopes whose file has become a package. Test by seeding a repo with a new uncovered directory and an uncovered base class, then measuring catch rate; second-order test is whether routing actually changes once the gap is closed.

   **This is the least-evidenced hypothesis in the document and the most differentiated.** Cursor scopes rules by `globs` and `AGENTS.md` has no scoping at all, but neither reports which directories match nothing; Claude Code routes on subagent `description` text with no notion of coverage; the multi-agent literature names the failure without instrumenting it — delegation "governed only by implicit conventions which fail silently" ([arXiv:2603.18043](https://arxiv.org/pdf/2603.18043)). No prior art was found for reporting coverage of an agent set over a repository, which means the metric is ours to define and there is nothing to validate against. Field evidence is n=1: two of four blind spots in an anonymized codeagent audit were scope gaps, one from a single-file scope surviving a refactor into three modules, one from a directory that was never in any agent's scope.

7. **Coverage reports drive scope inflation — the guardrail hypothesis (added 2026-08-02).** Observed once, and it undercuts hypothesis 6 if true: presented with an agent missing one directory, the field report's remedy expanded that agent to four architectural layers at once. Closing the gap that way trades a blindspot for an agent that triggers on everything and knows each layer shallowly — a coverage report measures whether code has an owner, never whether the owner is any good, and optimizing the first at the expense of the second is a net loss. Mitigation shipped alongside 6: a layer test that classifies the uncovered directory against the agent's existing layers and proposes a new agent rather than a fold when they differ, with the size ceilings still binding. Test by presenting the same gap report with and without the guardrail and measuring the resulting agent shapes. Until measured, hypothesis 6 should not ship a coverage number without it.

## Open questions

- **No FP/FN benchmarks for LLM doc audits exist.** Every conservatism claim is asserted. If repokit ships LLM claim-verification, it should label results as unproven-precision and consider building a small labeled eval — which would itself be first-of-kind.
- **No drift-rate measurements exist.** The 13–20% co-change figure is 2009-era code comments, not 2026 agent context files. Repokit's sync telemetry could produce the first real numbers **(repokit hypothesis)**.
- **Does deterministic linting improve agent outcomes at all?** Zero evidence either way — the entire linter niche is unvalidated. The mechanics are cheap enough that the bet is low-risk, but honesty requires calling it a bet.
- **What cadence does LLM auditing earn?** Per-PR (~$0.50–2) vs nightly vs weekly is currently decided by budget folklore. The AgentPatterns rule of thumb — continuous auditing pays only when drift outpaces correction — has no numbers behind it.
- **Does description drift actually cause mis-routing?** The chain is plausible (descriptions are the routing signal; routing is wording-sensitive) but the direct effect is unmeasured. A trigger-eval before/after on aged vs refreshed agentkit descriptions would test it directly **(repokit hypothesis)**.

  *Sharpened 2026-08-02:* there is a strictly easier version of this experiment worth running first. Aged-vs-refreshed wording is a subtle contrast with an ambiguous baseline; **covered-vs-uncovered** is not — either some agent claims the directory or none does. Run the coverage version to establish whether routing responds to scope at all, then attempt the wording version. If routing doesn't move on the unambiguous contrast, the subtle one isn't worth instrumenting.

- **Is an uncovered directory a defect? (added 2026-08-02)** Hypothesis 6 assumes uncovered code is a problem, and plenty of it isn't — thin CRUD, config, glue, generated output, anything an agent gets right from framework knowledge alone. There is no principled line between "needs an owner" and "correctly unowned," so the current default is a size threshold (≥10 files small/medium, ≥20 large) chosen by inspection, not measurement. A coverage metric with an arbitrary denominator invites optimizing the number rather than the outcome — see hypothesis 7. Whether coverage should be reported as a ratio at all, or only as an enumerated list of gaps the user accepts or closes, is unsettled.
- **Where is the auto-fix line?** Swimm auto-patched only trivial drift and punted the rest; OpenAI auto-merges most cleanup PRs. Whether repokit's sync should fix, draft, or only flag — per check type — is a design decision this research informs but doesn't settle.

- **Which claims in a doc are even falsifiable? (added 2026-08-04)** Removing layer 2 established that a *prescriptive* line can't be falsified by disobedience — only a *descriptive* one can be falsified at all. That split now decides what this document's checks may legitimately target, and nothing here measures how much of a real generated doc falls on each side. If most of `PRINCIPLES.md` is prescriptive, then most of it is permanently outside drift detection's reach, and the honest scope of "keeping docs in sync" is narrower than the premise implies. Worth counting on the sample docs before claiming coverage anywhere.

- **Does removing a signal reduce trust in the report? (added 2026-08-04)** The decay flag was wrong to ship, but it was also the only line in a sync report that ever said *something you documented may no longer hold.* What remains is quieter by design — an `Updated` block, a `Left alone` count, and reference failures. Whether a report that mostly confirms nothing changed keeps getting read is the same unmeasured question as the review channel, one signal poorer **(repokit hypothesis)**.
