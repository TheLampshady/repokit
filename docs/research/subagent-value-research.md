# Subagent Value and Payload — Research

**Written:** 2026-08-05
**Last updated:** 2026-08-05
**Original request:** Test the claim that choice-focused foundations docs empower agentkit's generated subagents because those agents are customized and focused — specifically, what a subagent's clean context and narrow scope are worth, and what belongs inside one.
**Charter:** `docs/research/CHARTER.md`
**Provenance:** Sourced claims cite primary sources inline; everything under Hypotheses is unmeasured. This doc stands alone.

## Summary

### Goal

Decide what agentkit's generated foundation agents should carry in their bodies, given that they are invoked as delegated workers running in their own context window rather than read as reference by the main conversation.

### Hypotheses

- **H1** — Isolation is the benefit; specialization is what makes isolation survivable.
- **H2** — Choice-band content is the only payload worth embedding, because everything else the agent can read on demand.
- **H3** — The template's expert-persona preamble buys nothing and is spending characters that worked code should have.
- **H4** — Pointing the agent at one named exemplar file captures most of the worked-implementation effect without embedding code or building a retrieval layer.

### Findings

- Subagent context isolation is a documented platform mechanism on Claude and Copilot, and delegation is decided by the `description`.
- Irrelevant and distant context measurably degrades model reasoning — the reason a clean window is worth something.
- The headline multi-agent uplift is research-task-specific; vendors say coding parallelizes worse.
- Expert personas in system prompts do not improve performance.
- Worked implementations outperform complete documentation as context, by roughly 2–4×.
- Real-world class-level code generation sits at 25–34% correctness against 84–89% on synthetic benchmarks.

## Key findings

Sourced claims only. Every bullet cites an external primary source — a bullet with nothing to cite is a hypothesis and belongs in the next section.

- **A subagent's context isolation is a real platform mechanism, not a metaphor** ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)) — "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions," and "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read." The same shape holds on Copilot: work is "carried out using a subagent… The subagent has its own context window" ([GitHub Copilot custom agents](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents)). Both platforms route by description — Claude "uses each subagent's description to decide when to delegate tasks."

- **What *does* reach a Claude custom subagent is narrower than the body, and wider than "nothing"** ([Claude Code subagents § What loads at startup](https://code.claude.com/docs/en/sub-agents)) — the initial context is the agent's own system prompt, the delegation message, **every level of the CLAUDE.md hierarchy** the main conversation loads, a git-status snapshot, and any preloaded skills. Conversation history, files already read, output style, and auto memory do not reach it. Only the built-in Explore and Plan agents skip CLAUDE.md, and "there is no frontmatter field or per-agent setting to change which agents skip them."

- **Irrelevant context degrades reasoning measurably — this is the mechanism behind "clean context"** ([Shi et al., ICML 2023](https://arxiv.org/abs/2302.00093)) — GSM-IC adds irrelevant sentences to arithmetic word problems and finds "model performance is dramatically decreased when irrelevant information is included," across every prompting technique tested. Effect sizes are in the paper body, not the abstract; not independently verified here.

- **Position inside a long context changes accuracy, even for long-context models** ([Liu et al., TACL 2023](https://arxiv.org/abs/2307.03172)) — "performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models." A U-shaped curve, not a cliff at the window limit.

- **Degradation with input length reproduces across 18 current models, and distractors amplify it** ([Chroma, *Context Rot*, 2025-07-14](https://www.trychroma.com/research/context-rot)) — Hong, Troynikov, and Huber extend needle-in-a-haystack with controlled needle–question similarity, distractor placement, and haystack coherence, and find "model performance varies significantly as input length changes, even on simple tasks," with distractors having non-uniform, amplified impact at longer contexts. Vendor-adjacent (a vector-DB company), so treated as corroboration of the two peer-reviewed results above rather than as their basis.

- **Vendor guidance names context pollution as the reason to split work, and sets the split test on isolation** ([Anthropic, *When to use multi-agent systems*](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)) — "When an agent's context accumulates information from one subtask that is irrelevant to subsequent subtasks, context pollution occurs. Subagents provide isolation, with each operating in its own clean context focused on its specific task." The operative rule is context-centric, not problem-centric: "Work should only be split when context can be truly isolated." Also: "The primary benefit of parallelization is thoroughness, not speed," multi-agent approaches "typically use 3-10x more tokens than single-agent approaches for equivalent tasks," and teams routinely over-engineer — "months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results." Single vendor blog: a lead, not a basis, per the charter's evidence order.

- **The headline multi-agent uplift is research-task-specific, and coding is called out as the weaker case** ([Anthropic, *How we built our multi-agent research system*](https://www.anthropic.com/engineering/multi-agent-research-system)) — the "90.2%" figure is Claude Opus 4 lead with Sonnet 4 subagents "on our internal research eval," an unpublished benchmark. The same post scopes it: multi-agent systems "excel at valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools," while "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit… most coding tasks involve fewer truly parallelizable tasks than research." It also states the delegation requirement directly: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information."

- **Expert personas in system prompts do not improve performance** ([Zheng et al., Findings of EMNLP 2024](https://aclanthology.org/2024.findings-emnlp.888/)) — 162 roles across 6 interpersonal relationship types and 8 expertise domains, 2,410 factual questions, 4 model families: "adding personas in system prompts does not improve model performance" against a no-persona control. Per-question oracle persona selection *does* help, but automatic selection performs "no better than random selection." Scope limit: factual QA, not code generation; the paper's abstract was reversed between its 2023 preprint and the October 2024 version, so cite the published version.

- **Worked implementations beat complete documentation as context, by roughly 2–4×** ([Rahman, Khatoonabadi & Shihab, *Beyond Synthetic Benchmarks*](https://arxiv.org/abs/2510.26130)) — seven models over 400 real classes (RealClassEval) plus 100 synthetic (ClassEval). Full docstrings — "function descriptions, parameter types, and return specifications" for every program unit — bought **1–3%** correctness over signatures alone. Retrieving the top *k*=2 most similar class skeletons and appending "their complete implementations (signature, docstrings, and body)" bought **4–7%**. Scope limit that matters: the documentation ablation was docstrings *of the unit under construction*, not project-level decision content, so this finding ranks two context *forms* and says nothing directly about foundations docs.

- **The real-world gap this all sits inside is large** ([Rahman et al.](https://arxiv.org/abs/2510.26130)) — "LLMs achieve 84 to 89% correctness on synthetic benchmarks, they attain only 25 to 34% on real-world class tasks," with "minimal distinction between familiar and novel codebases." Training exposure to a repo doesn't substitute for context about it.

- **Missing repo context produces reinvention, not just error** ([Liao et al., *A³-CodGen*, arXiv 2312.05772 v5](https://arxiv.org/abs/2312.05772)) — the framework separates repository context into local-aware, global-aware, and third-party-library-aware, targeting "fewer potential logical errors, code redundancy, and library-induced compatibility issues," and reports code with "a higher reuse rate, compared to human developers." Reuse-rate numbers are in the paper body; abstract-level only, not independently verified here.

- **Multi-agent gains are often minimal, and the failures are design failures** ([Cemri et al., *Why Do Multi-Agent LLM Systems Fail?*, NeurIPS 2025 Datasets & Benchmarks](https://arxiv.org/abs/2503.13657)) — "Despite enthusiasm for Multi-Agent LLM Systems (MAS), their performance gains on popular benchmarks are often minimal." 150 traces hand-annotated at κ = 0.88, 1600+ traces total, yielding 14 failure modes in 3 categories: system design, inter-agent misalignment, task verification. The counter-position from practice is that decision-making becomes too dispersed and context is not shared thoroughly enough between agents ([Cognition, *Don't Build Multi-Agents*](https://cognition.com/blog/dont-build-multi-agents)).

- **Curation, not volume, is the stated design target** ([Anthropic, *Effective context engineering*](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)) — find "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"; models have an "attention budget" that "every new token" depletes; system prompts should sit at the "right altitude," neither hardcoded brittle logic nor "vague, high-level guidance that fails to give the LLM concrete signals"; and just-in-time retrieval keeps "lightweight identifiers (file paths, stored queries, web links)" in context and loads content through tools at runtime. On subagents: "specialized sub-agents can handle focused tasks with clean context windows," returning condensed summaries of "typically 1,000-2,000 tokens."

- **No benchmark measures decision-band project documentation as agent payload** *(absence claim)* — searches across the repository-level code-generation literature, the context-engineering literature, and the multi-agent evaluation literature surfaced ablations over docstrings, retrieved implementations, dependency context, and API signatures. None isolates *team-decision* content — invariants, sanctioned extension procedures, uncovered scope — as a context condition. The user's claim is therefore untested rather than contradicted.

## Hypotheses

Positions developed with the user rather than found in literature: unmeasured, and the reason the Actions below are worth taking. IDs are permanent — assigned once, never renumbered, never reused. New ones append.

**H1 — Isolation is the benefit of a foundation agent, and specialization is what makes isolation survivable rather than a separate benefit of its own** · *open* · added 2026-08-05
- **Unsourced because:** the two halves are each sourced — isolation removes measured degradation (Shi, Liu, Chroma), and platform docs confirm what fails to cross the boundary — but nothing published tests the joint claim that a narrow scope is what lets an agent function *without* the parent's accumulated context. Searched: subagent context isolation evaluations, MAS failure taxonomies, agent-scoping benchmarks.
- **Check:** take 5 tasks touching one foundation in a real project. Run each twice: (a) main conversation with `docs/FOUNDATIONS.md` already read, (b) delegated foundation agent with no conversation history. Count invariant violations and reinvented implementations in each arm. If (b) is not at least as good, isolation is costing more than it returns and the payload is under-specified.

**H2 — Choice-band content is the only thing worth embedding in a generated agent, because everything else it can read on demand** · *open* · added 2026-08-05
- **Unsourced because:** the closest measurement ranks docstrings against retrieved implementations (Rahman et al.), neither of which is decision content; the absence claim above records the gap. Searched: repository-level code generation ablations, RAG-for-code context conditions, AGENTS.md-style instruction-file evaluations.
- **Check:** ablate a generated foundation agent's body. Arm A: full body. Arm B: Architecture Context, Working Directories, and Key Files only — invariants, `Extend by`, and `Doesn't cover` removed. Same 5 tasks. Count invariant violations and cases where the agent built something the foundation already covered. A null result means the embedded choice content isn't doing the work and the agent should be a pointer instead.

**H3 — The template's expert-persona preamble is dead weight, and the characters belong to worked code** · *open* · added 2026-08-05
- **Unsourced because:** Zheng et al. measured personas on factual QA with no project payload attached, so it does not transfer to a code agent carrying real paths and invariants. No study found that ablates role framing *while holding a project-specific payload constant*. Searched: persona/role prompting for code generation, system-prompt role ablations.
- **Check:** strip the two-role preamble in `foundation-agent.template.md` to a single line, spend the reclaimed characters on a second worked call site, and run the same 5 tasks. Looking for no regression in behaviour attributable to the framing — specifically that the agent still declines out-of-scope work and still refuses to edit foundation source.

**H4 — Pointing the agent at one named exemplar file captures most of the worked-implementation effect, and does so better than either embedding the code or telling the agent to go find it** · *open* · added 2026-08-05
- **Unsourced because:** Rahman et al. supplied retrieved implementations through embedding similarity over a prepared corpus and pasted them into the prompt; nobody has measured the address-only version, where the agent is told which file to read and reads it with the tools it already has. The context7 half of this is a scope reading rather than a measurement — context7 serves third-party library documentation, which is A³-CodGen's *third-party-library-aware* dimension, while the +4–7% came from implementations drawn from the same corpus as the target, i.e. the *local-aware* dimension. Searched: MCP documentation servers as code-context sources, retrieval-instruction vs retrieval-pipeline comparisons, just-in-time context loading evaluations.
- **Check:** add the exemplar pointer to one project's generated agents. Over 10 tasks, log two things separately: (a) whether the agent read the named file before writing, and (b) convention violations and duplicate implementations, against the same count from the 10 tasks before the change. Splitting the two matters — a null result with high read rates means exemplars don't help, while a null result with low read rates means the instruction was ignored, and those call for opposite responses.
- **Why the address rather than the code:** embedding a 40-line worked file costs roughly 1,500 characters against a 10,000-character budget and creates a second copy of code inside a doc, which is the drift surface dockit exists to remove. A path plus a symbol costs ~80 characters and, when the file or the symbol goes, breaks into a checkable claim sync can verify with a grep. This is the just-in-time pattern from the Anthropic context-engineering finding above, applied at generation time instead of runtime.

## How this applies to your request

Your claim splits cleanly along the evidence, and only one half is in trouble.

The **focus** half holds up, but not for the reason it's usually given. A specialized agent isn't better because it is an expert — Zheng et al. is a direct hit against that reading, and the persona language in the current template is exactly the kind of framing they measured as inert. It's better because isolation removes context that measurably degrades reasoning: irrelevant material in the prompt (Shi et al.), material sitting in the middle of a long window (Liu et al.), and sheer length (Chroma). Those effects are why a clean window is worth paying 3–10× tokens for. So the honest statement of your claim is *inverted from how it sounds*: focus doesn't add expertise, it subtracts interference — and the customization exists to make that subtraction safe, by ensuring the agent still knows what it needs after the parent's context is gone. That inversion is what H1 tests.

The **content** half is where the actionable finding is, and it partly cuts against the shape you have. Rahman et al. is the closest thing to a measurement of what you're proposing, and its ranking is uncomfortable: complete documentation of the thing being built bought 1–3%, while worked implementations of similar code bought 4–7%. Your foundations entries are much better than docstrings — they carry non-derivable decisions rather than restating signatures, which is the whole point of the choice band — but the template currently spends most of its hot-memory budget on prose blocks and carries a single canonical call site. If the ranking transfers at all, that allocation is backwards.

On your question about context7: it doesn't get you the percentage. The +4–7% came from implementations retrieved from the same corpus as the target — the local-aware dimension in A³-CodGen's split. context7 serves the third-party-library-aware dimension: excellent for "how does this framework's API work," structurally unable to answer "how does *this team* build one of these." The two are complementary, not substitutable, and the one your claim depends on is the one context7 doesn't cover. The charter also rules out building a retrieval layer, and embedding whole worked files would put a second copy of the code inside a doc — the drift surface dockit exists to remove — while eating roughly 15% of the body budget per file. What's left is the cheapest option and probably the right one: precompute the *address* rather than the content. One exemplar line per foundation, naming the file worth reading before writing, and an instruction to read it. That costs ~80 characters, can't rot silently because a moved path is a checkable claim, and asks the agent to read one named file rather than to search well — a much lower bar for compliance. That's H4, and A5 is where the address comes from.

Two constraints bound all of this. Delegation is decided by the `description` alone, so a payload improvement is invisible if the agent never gets routed to — the body can't fix a routing failure. And Anthropic's own scoping says coding parallelizes worse than research, with shared-context and interdependent-decision work explicitly a poor fit; MAST and Cognition both land in the same place from the failure side. Since these agents are delegated workers by design, the reasonable reading is that the foundation agent is a good fit precisely where its territory is genuinely separable — which is the same boundary the grouping rules already draw, arrived at from a different direction.

## Actions

- **A1 — Add an `Exemplar` line per owned foundation to `skills/agentkit/references/templates/foundation-agent.template.md`, and a read-it-first instruction ahead of the Custom Patterns section.** · *building* — The line carries a path, the **symbol** to look at, and one clause on why that file is representative — `` `app/notifications/order_confirmed.py` → `class OrderConfirmedNotification` — newest consumer, added 2026-05 ``. Symbol rather than line range: numbers move whenever anything above them is edited, so a range goes wrong while the code is still good, whereas a symbol goes wrong exactly when the thing being pointed at is renamed or deleted. Both are greppable; only one is stable. The context7 boundary belongs in the agent's `Research` ordering (local question → exemplar, framework question → context7), not in a prose disclaimer the agent doesn't act on.
  **Because:** H4, [Rahman et al.](https://arxiv.org/abs/2510.26130), [A³-CodGen](https://arxiv.org/abs/2312.05772), [Anthropic on just-in-time identifiers](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

- **A2 — Hold embedded code to what can't be pointed at, and make prose yield first when the 10,000-character budget binds.** · *building* — In `foundation-agent.template.md` and the size check in `skills/agentkit/references/guides/GENERATION.md`: keep the single canonical call site (it's a call *site*, not a file, so no address substitutes for it), require the named anti-pattern to appear as real code where one exists in the repo, and rank the exemplar pointer above every prose block. Do not grow the number of embedded code excerpts — that budget goes to addresses now.
  **Because:** H2, [Rahman et al.](https://arxiv.org/abs/2510.26130), [Anthropic on the attention budget](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

- **A3 — Cut the two-responsibility persona preamble in `foundation-agent.template.md` to a single line stating the agent's scope and its doc-edit authority.** · *building* — Keep the authority statement — it is a permission boundary, not framing — and drop the expert assertion.
  **Because:** H3, [Zheng et al.](https://aclanthology.org/2024.findings-emnlp.888/)

- **A4 — Add a self-sufficiency check to `skills/agentkit/references/guides/GENERATION.md`: the generated body must be actionable by an agent that has no conversation history, no files already read, no output style, and no auto memory.** · *building* — Name those four exclusions explicitly, and note that on Claude the CLAUDE.md hierarchy *does* reach a custom subagent while on other platforms it may not, so a rule that must hold belongs in the body rather than being assumed inherited.
  **Because:** H1, [Claude Code subagents](https://code.claude.com/docs/en/sub-agents), [GitHub Copilot custom agents](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents)

- **A5 — Add the exemplar-selection rule to `skills/agentkit/references/guides/GENERATION.md`, computed at generation time from inputs agentkit already reads.** · *building* — Take the foundation's `Consumers` column from `docs/FOUNDATIONS.md`, pick the most recently *added* file in that set (`git log --diff-filter=A`), and record its path, the symbol to read, and the add date. Rationale to state in the guide: the newest consumer is the last time someone did this task and got it through review, so it reflects current practice rather than the oldest surviving pattern. Skip candidates inside a `hotspot` foundation's tree — a shape under active dispute shouldn't be the thing new code copies — and when every candidate is a hotspot, emit no exemplar and say so in the report rather than pointing at a pattern the team is arguing about.
  **Because:** H4, [Rahman et al.](https://arxiv.org/abs/2510.26130)

## Decisions (deliberately not doing)

- **Not recommending context7 as the source of worked implementations.** It serves third-party library documentation; the measured effect came from implementations local to the target's own corpus. Complementary, not substitutable.
- **Not building or wrapping a similarity-retrieval index over the project's own code** to reproduce Rahman et al.'s RAG condition. The charter rules out a retrieval layer, and A1 tests whether an address gets most of the way there first.
- **Not embedding whole worked files in a generated agent's body.** ~1,500 characters each against a 10,000-character budget, and it puts a second copy of the code inside a doc — new drift surface, in exchange for content the agent can read on demand. The pointer supersedes it.
- **Not asking the agent to search for a good example on its own.** Rejected in favour of a named file: "find the nearest implementation" is a judgment call made without the context to make it, and an agent that searches badly and an agent that skipped the step produce identical output.
- **Not relying on expert-persona framing as a mechanism.** It may stay as prose for a human reader, but nothing in the design gets to depend on it.
- **Not revisiting how foundations are grouped into agents or how many agents there should be.** Settled on other grounds and out of scope for this run; this doc only addresses what goes inside an agent once it exists.
- **Not treating the 90.2% research-eval figure as evidence for coding agents.** Unpublished internal benchmark, research-task shaped, and the same post scopes coding out.

## Open questions

- **A claim in `repo-maintenance-research.md` is now contradicted by the platform docs and is left uncorrected on purpose.** That doc states default subagents "don't see CLAUDE.md or AGENTS.md." The current Claude Code documentation says every level of the CLAUDE.md hierarchy loads into a custom subagent's initial context, and that only the built-in Explore and Plan agents skip it. What *is* absent is conversation history, files already read, output style, and auto memory. Flagged here rather than edited, at the user's direction. Worth deciding whether any part of the FOUNDATIONS-pointer design was justified by the stale reading.
- **Whether the docstring result transfers to decision content at all.** Rahman et al.'s 1–3% documentation arm was docstrings of the unit under construction — derivable, overview-band material by repokit's own split. Choice-band content is different in kind, and might behave more like the retrieved-implementation arm than the documentation arm. Nothing measures this; H2 is the closest available substitute and it only tests presence versus absence, not the ranking.
- **Antigravity's subagent isolation semantics are unverified.** Isolation and description-based routing were confirmed on Claude and Copilot from primary docs. Antigravity was not checked in this run, so the cross-platform claim currently rests on two of three platforms.
- **Whether delegation is worth 3–10× tokens for small foundation tasks.** No threshold found in any source, and the Anthropic guidance explicitly warns that better single-agent prompting often matches a multi-agent build. A one-line change inside a foundation's directory probably shouldn't be delegated, but nothing here says where the line is.
- **Instruction compliance is still the weak point in A1, even reduced to "read this file."** Anthropic's verification-subagent guidance — "Without explicit requirements for comprehensive validation, verification agents take shortcuts" — suggests shortcuts are the default, and a skipped read is invisible in the output. Naming the file lowers the bar as far as it goes; H4's check logs the read rate separately for this reason, but nothing here establishes what rate to expect.
- **Where the exemplar address should live is unsettled.** A5 has agentkit compute it at generation time, which keeps the change inside one skill and needs no schema change. The alternative is an `Exemplar` field on the FOUNDATIONS.md row, computed once by dockit and read by every consumer — less recomputation, and it would survive for human readers too, but it's a schema addition to a tooling contract and isn't proposed here. Worth deciding before a second consumer needs the same address.
- **Nothing keeps the exemplar current between syncs.** The address breaks loudly when the file is deleted or the symbol renamed, which sync catches by grepping for the symbol. A file that merely stops being representative — the pattern moved on, this one is now the oldest example rather than the newest — breaks silently, and the add date is the only signal a reader gets.
- **The symbol anchor is unverified against real languages.** A grep for `class OrderConfirmedNotification` is unambiguous in Python; a symbol that appears in a dozen files, a name that collides with an import, or a language where the declaration spans lines oddly (Go interfaces, TypeScript overloads) may make the check noisy or vacuous. Shipped on reasoning, not on a trial across languages.
- **The word "rot" collided with the published literature; the charter now carries both senses.** Resolved 2026-08-05 by the user: the existing entry became **Rot and drift**, and **Context rot** was added as a separate gloss for the published sense. The distinction that made it worth separating — rot and drift are properties of the doc, context rot is a property of the reader — is not itself measured, and it's the kind of clean split that could turn out to be too clean. Watch for a case where a doc's length is what makes it go unverified.
